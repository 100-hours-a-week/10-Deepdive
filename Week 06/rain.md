# RAG에서 Chunking Strategy가 Retrieval 정확도와 Context 품질에 미치는 영향을 설명하시오.

## 청크 크기, 청크 중첩, 의미 단위 분할 여부에 따라 검색 결과와 LLM 응답이 어떻게 달라질 수 있는지 구체적으로 서술하시오.

---

## 0. RAG가 뭔가

### 일반 LLM의 한계

일반 LLM(챗GPT, 클로드 등)은 학습할 때 외운 지식으로만 답한다.
마치 암기 시험을 보는 학생과 같다.
모르는 정보를 물어보면 모른다고 하지 않고, 그럴듯하게 지어낸다 (환각, Hallucination).
특히 회사 내부 문서, 최신 정보, 전문 자료처럼 학습 데이터에 없는 내용은 틀린 답을 낼 가능성이 크다.

### RAG의 해결 방식

**RAG (Retrieval-Augmented Generation)** = 검색으로 보강된 생성.
질문이 들어오면 관련 문서를 먼저 찾고(Retrieval), 그 문서를 참고해서 답을 만든다(Generation).
오픈북 시험을 보는 학생과 비슷하다 — 책(문서)을 찾아보고 답한다.

    질문 입력 ("우리 회사 휴가 규정이 뭐야?")
      ↓
    Retrieval (검색) — 문서 중 휴가 관련 부분을 찾음
      ↓
    찾은 내용을 LLM에 전달 ("이 문서 보고 답해줘")
      ↓
    Generation (생성) — LLM이 문서를 참고해서 답변 작성

핵심은, LLM이 모든 걸 외우는 게 아니라 필요할 때마다 문서를 찾아서 그걸 보고 답한다는 점이다.

## 1. 청킹(Chunking)이 뭔가

### 왜 필요한가

문서를 통째로 LLM에 넣을 수 없다.

- 용량 제한: 100페이지짜리 문서를 한 번에 넣을 수 없음
- 관련성 문제: 휴가 질문인데 출장비, 복장 규정까지 다 들어가면 LLM이 헷갈림

그래서 문서를 미리 작은 조각으로 잘라두고, 질문과 관련된 조각만 찾아서 전달한다.
**이 "작은 조각으로 자르는 것"을 청킹이라 하고, 어떻게 자르느냐가 Chunking Strategy(청킹 전략)다.**

    100페이지 규정 문서
      ↓ (청킹)
    청크1 / 청크2 / 청크3 / 청크4 / 청크5 / ...
    (각 청크는 미리 잘라서 저장해둠 → 질문이 오면 그중 관련된 것만 검색)

### Retrieval과 Context 정리

| 용어 | 의미 |
|------|------|
| Retrieval (검색) | 질문과 관련된 청크를 찾아내는 과정 |
| Context (맥락) | 찾아낸 청크를 LLM에게 전달하는 내용물, LLM이 답을 만들 때 참고하는 재료 |
| Retrieval 정확도 | 진짜 관련 있는 청크를 정확히 찾아왔는가 |
| Context 품질 | 전달된 내용이 완전하고 깔끔한가 — 필요한 정보는 다 있고, 불필요한 내용은 안 섞여 있는가 |

> 청킹 전략이 나쁘면 두 가지 문제가 동시에 생길 수 있다.
> 검색은 됐는데 정작 필요한 정보가 잘려 있거나(Context 품질 저하), 관련 없는 정보가 같이 검색돼서(Retrieval 정확도 저하) LLM의 응답 품질이 떨어진다.

## 2. 청크 크기 (Chunk Size)가 미치는 영향

### 정의

조각 하나의 길이를 얼마로 할지 정하는 것. 보통 글자 수나 토큰 수로 정한다.

### 예시 원문

> "연차는 입사 1년 차부터 15일이 주어진다. 사용하지 않은 연차는 다음 해로 이월되지 않는다. 단, 회사 사정으로 인한 미사용은 예외로 한다."

### 크기별 비교

| 청크 크기 | 잘리는 방식 | 검색 결과 | LLM 응답 |
|-----------|------------|-----------|----------|
| 너무 작음 (약 20자) | "연차는 입사 1년 차부터" / "15일이 주어진다" / "사용하지 않은 연차는" 등으로 잘게 분리 | "15일이 주어진다"만 단독으로 검색됨 | 무엇이 15일인지 알 수 없어 "확인이 필요합니다" 식으로 답하거나, 추측해서 틀린 답을 낼 위험 |
| 적당함 (약 100자) | "연차는 입사 1년 차부터 15일이 주어진다. 사용하지 않은 연차는 다음 해로 이월되지 않는다." 통째로 한 청크 | 질문과 정확히 맞는 청크가 검색됨 | "연차는 15일이며, 이월되지 않습니다"처럼 정확한 답변 |
| 너무 큼 (약 500자) | 휴가 규정 + 출장비 규정 + 복장 규정까지 한 청크에 다 포함 | 휴가 질문인데 출장비, 복장 내용까지 같이 검색됨 | LLM이 핵심을 찾기 어려워하고, 불필요한 내용까지 포함된 장황한 답변을 만들거나 엉뚱한 부분을 답할 위험 |

### 결론

청크가 너무 작으면 문장이 중간에 끊겨 **Context 품질**이 떨어지고 (필요한 정보가 불완전),
청크가 너무 크면 여러 주제가 섞여 **Retrieval 정확도**가 떨어진다 (관련 없는 내용까지 같이 검색됨).
적절한 청크 크기는 보통 하나의 완결된 의미 단위(문장 또는 짧은 문단)를 포함하는 수준이 권장된다.

## 3. 청크 중첩 (Chunk Overlap)이 미치는 영향

### 정의

청크를 자를 때 경계 부분을 완전히 끊지 않고 살짝 겹치게 자르는 것.
앞 청크의 끝부분을 다음 청크의 시작 부분에도 포함시킨다.

### 예시 — "이월 안 된 연차는 어떻게 되나요?" 질문

원문: *"...연차는 다음 해로 이월되지 않는다. 단, 회사 사정으로 인한 미사용은 예외로 한다."*

| 중첩 여부 | 청크 구성 | 검색·응답 결과 |
|-----------|-----------|----------------|
| 중첩 없음 | 청크A: "...연차는 다음 해로 이월되지 않는다." / 청크B: "단, 회사 사정으로 인한 미사용은 예외로 한다." (완전히 분리) | 검색에서 청크A만 잡히면 예외 조항(청크B)이 누락됨 → "연차는 이월되지 않습니다"라고만 답해 불완전한 정보 전달 |
| 중첩 있음 | 청크A: "...연차는 다음 해로 이월되지 않는다. 단, 회사 사정으로 인한..." / 청크B: "다음 해로 이월되지 않는다. 단, 회사 사정으로 인한 미사용은 예외로 한다." (경계 부분이 겹침) | 어느 청크가 검색되든 예외 조항까지 포함되어 있음 → "원칙적으로 이월되지 않지만, 회사 사정으로 인한 미사용은 예외입니다"처럼 정확하고 완전한 답변 |

### 중첩의 트레이드오프

- 장점: 청크 경계에 걸친 중요 정보(예외 조항, 단서 조항, 이어지는 문맥)를 양쪽 청크 모두 보존 → Context 품질 향상
- 단점: 중첩이 많을수록 같은 내용이 여러 청크에 중복 저장되어 저장 공간이 늘어나고, 검색 결과에 비슷한 내용의 청크가 여러 개 나와 중복도가 높아질 수 있음

### 결론

중첩이 없으면 경계에 걸친 정보가 누락되어 **Context 품질**이 떨어진다.
중첩이 적절하면(일반적으로 청크 크기의 10~20% 수준) 문맥이 보존되지만, 과도한 중첩은 저장 비용과 중복 검색이라는 부작용을 낳는다.

## 4. 의미 단위 분할 (Semantic Chunking)이 미치는 영향

### 정의

지금까지의 청크 크기·중첩은 모두 글자 수 기준의 고정 길이 분할이었다.
**의미 단위 분할**은 글자 수가 아니라 **내용(주제)이 바뀌는 지점**을 찾아서 자르는 방법이다.
문장 간 의미를 분석해서, 앞 문장과 다음 문장의 주제가 크게 다르면 그 지점에서 분할한다.

### 예시 — "출장비 한도가 얼마야?" 질문

원문: *"연차는 입사 1년 차부터 15일이 주어진다. 출장비는 건당 5만원 한도로 지급된다. 복장은 비즈니스 캐주얼을 원칙으로 한다."*

| 분할 방식 | 청크 구성 | 검색·응답 결과 |
|-----------|-----------|----------------|
| 고정 길이 분할 | "...연차는 15일. 출장비는 건당 5만원 한도. 복장은 비즈니스 캐주얼..." 한 청크에 휴가·출장비·복장이 모두 섞임 | 출장비 질문에도 연차·복장 내용까지 같이 검색됨 → LLM이 관련 없는 내용까지 같이 읽어야 해서 응답이 장황해지고 정확도가 떨어짐 |
| 의미 단위 분할 | "출장비는 건당 5만원 한도로 지급된다" 만 별도 청크로 분리 (연차, 복장과 분리됨) | 출장비 질문에 정확히 출장비 청크만 검색됨 → "5만원입니다"처럼 간결하고 정확한 답변 |

### 의미 단위 분할의 트레이드오프

- 장점: 한 청크에 한 가지 주제만 담겨서, 검색했을 때 관련 없는 내용이 섞이지 않음 → Retrieval 정확도와 Context 품질 동시 향상
- 단점: 문장 간 의미를 분석하는 과정이 추가로 필요해서 고정 길이 분할보다 처리 시간과 비용이 더 든다

### 결론

의미 단위로 분할하면 한 청크 = 한 주제가 되어 **Retrieval 정확도**가 높아지고(불필요한 청크가 안 걸림),
**Context 품질**도 좋아진다(LLM이 받는 내용이 깔끔함). 다만 구현 복잡도와 처리 비용이 늘어난다.

## 5. 세 요소가 Retrieval·Context에 미치는 영향 종합

| 요소 | 문제 상황 | Retrieval 정확도 | Context 품질 | 비고 |
|------|-----------|-------------------|----------------|------|
| 청크 크기 — 너무 작음 | 문장이 중간에 끊김 | 영향 적음 | 하락 (정보 불완전) | |
| 청크 크기 — 너무 큼 | 여러 주제 혼입 | 하락 (관련없는 청크도 검색) | 하락 (핵심 흐려짐) | |
| 청크 중첩 — 없음 | 경계 정보(예외조항 등) 손실 | 영향 적음 | 하락 (불완전한 답변) | |
| 청크 중첩 — 과도함 | 중복 청크 다수 검색 | 하락 (중복으로 인한 혼란) | 영향 적음 | 저장 비용 증가 |
| 의미 단위 분할 — 미적용 | 한 청크에 여러 주제 혼재 | 하락 | 하락 | 고정 길이 분할의 근본 한계 |
| 의미 단위 분할 — 적용 | 한 청크 = 한 주제 | 상승 | 상승 | 처리 비용 증가 |

---

## 6. 결론

> **청크 크기, 청크 중첩, 의미 단위 분할 — 셋 다 목적은 하나다.**
> LLM에게 "딱 필요한 만큼, 딱 정확한 내용"을 전달하는 것.
> 어느 하나라도 적절하지 않으면 — 너무 적어도, 너무 많아도, 주제가 섞여 있어도 —
> Retrieval 정확도와 Context 품질이 동시에 떨어지고, 결과적으로 LLM의 응답 품질도 저하된다.

| 권장 전략 | 효과 |
|-----------|------|
| 적절한 크기 (문장/문단 단위 유지, 대략 100~300토큰) | 의미 보존 + 핵심 유지 |
| 적절한 중첩 (청크 크기의 10~20% 수준) | 경계 정보 보존, 과도한 중복 방지 |
| 의미 단위 분할 적용 | 한 청크 = 한 주제 → Retrieval 정확도와 Context 품질 동시 향상 |

결국 좋은 Chunking Strategy란, 검색 시스템이 "관련된 것만 정확히 찾아오고", LLM이 "필요한 정보를 빠짐없이, 군더더기 없이" 받을 수 있도록 문서를 설계하는 작업이다.
