# ReAct Pattern: Reasoning과 Acting을 반복하는 Agent 문제 해결 방식

## 1. 배경

LLM 기반 Agent는 단순히 질문에 답하는 모델을 넘어, 스스로 판단하고 도구를 사용하며 문제를 해결하는 방향으로 발전하고 있다.

이때 중요한 패턴 중 하나가 **ReAct Pattern**이다.

ReAct는 다음 두 가지를 결합한 방식이다.

- **Reasoning**: LLM이 현재 상황을 해석하고 다음 행동을 판단하는 과정
- **Acting**: 판단에 따라 검색, 계산, API 호출, 코드 실행 등 실제 행동을 수행하는 과정

즉, ReAct Pattern은 Agent가 생각만 하는 것이 아니라, **생각하고 행동하고 관찰한 뒤 다시 생각하는 구조**를 가진다.

---

## 2. ReAct Pattern이란?

ReAct는 **Reasoning + Acting**의 합성어이다.

기존 LLM은 보통 한 번의 입력을 받고, 내부 지식에 기반해 한 번에 답을 생성한다.

하지만 현실의 문제는 한 번의 판단만으로 해결하기 어렵다.

**예시 상황**

> "이번 주 발표 주제에 맞는 최신 논문을 찾아 요약하고, 발표 자료 구조까지 만들어줘."

이 문제를 해결하려면 Agent는 여러 단계를 거쳐야 한다.

1. 사용자의 요구를 분석한다.
2. 필요한 정보를 검색한다.
3. 검색 결과를 확인한다.
4. 관련성이 낮은 정보는 제외한다.
5. 핵심 내용을 정리한다.
6. 발표 자료 형식으로 재구성한다.

ReAct Pattern은 이러한 과정을 한 번만 하고 끝내는 것이 아니라 **반복적인 루프**로 수행한다.

특히 **Agent가 사용하는 도구가 많아질수록** ReAct의 중요성이 커진다.

---

## 3. 기본 흐름

ReAct Pattern의 기본 흐름은 다음과 같다.

```text
문제 입력
  ↓
Reasoning: 현재 문제를 이해하고 다음 행동을 결정
  ↓
Acting: 검색, 계산, 도구 호출 등 실제 행동 수행
  ↓
Observation: 행동 결과를 관찰 (해봤더니 어떤 결과가 나왔나?)
  ↓
Reasoning: 관찰 결과를 반영해 다음 판단 수정
  ↓
반복
  ↓
최종 응답
```

핵심은 **Observation이 다음 Reasoning에 반영된다**는 점이다.

Agent는 처음 생각이 틀릴 수 있다는 전제를 가지고, 행동 결과를 통해 자신의 판단을 계속 보정한다. 그 이후 충분한 근거가 모이면 최종 응답 생성!

---

## 4. 반복 단계 예시

예시 질문:

> "서울에서 내일 비가 오면 실내 데이트 코스를 추천해줘."

ReAct 방식으로 처리하면 다음과 같다.

| 단계 | 내용 |
|---|---|
| Reasoning 1 | 내일 서울 날씨를 확인해야 한다고 판단 |
| Acting 1 | 날씨 정보를 검색하거나 날씨 API 호출 |
| Observation 1 | 내일 오후에 비가 올 확률이 높다는 결과 확인 |
| Reasoning 2 | 실내 중심 코스를 추천해야 한다고 판단 |
| Acting 2 | 미술관, 전시, 카페, 영화관 등 장소 정보 검색 |
| Observation 2 | 운영 시간, 위치, 혼잡도, 이동 거리 확인 |
| Reasoning 3 | 동선이 자연스럽고 비를 덜 맞는 코스로 재구성 |
| Final Answer | 사용자에게 맞는 실내 데이트 코스 제안 |

이 과정에서 Agent는 처음부터 답을 확정하지 않는다.

관찰 결과에 따라 추천 방향을 계속 조정한다.

---

## 5. Observation이 중요한 이유

Observation은 Acting의 결과이다.

즉, Agent가 외부 세계와 상호작용한 뒤 얻는 정보이다.

Observation이 중요한 이유는 세 가지로 정리할 수 있다.

### 1. 잘못된 가정을 수정할 수 있다

Agent가 처음에는 "내일 비가 올 것 같다"고 생각했더라도, 실제 날씨 정보를 확인했을 때 맑다면 추천 방향은 완전히 달라져야 한다.

관찰 결과는 Agent가 자신의 추측을 사실에 맞게 수정하도록 만든다.

### 2. 최신 정보와 실제 데이터를 반영할 수 있다

LLM의 내부 지식은 학습 시점에 머물러 있을 수 있다.

하지만 ReAct 방식에서는 검색, DB 조회, API 호출 등을 통해 현재 정보를 확인할 수 있다.

그래서 가격, 일정, 날씨, 재고, 정책처럼 자주 변하는 정보에 더 강하다.

### 3. 문제 해결 경로를 점진적으로 개선할 수 있다

복잡한 문제는 한 번에 정답으로 가기 어렵다.

Observation을 반영하면 Agent는 다음 행동을 더 정확하게 선택할 수 있다.

결과적으로 문제 해결 과정이 더 유연해진다.

---

## 6. 관찰 결과 반영이 응답 품질에 미치는 영향

ReAct Pattern은 Agent의 응답 품질을 여러 측면에서 향상시킨다.

### 정확성

관찰 결과를 통해 사실 확인이 가능해진다.

Agent가 내부 지식만으로 답할 때보다 오류 가능성이 줄어든다.

Observation을 제대로 반영하지 않거나, 도구 실패를 무시하면 Agent는
실제 근거 없이 답변을 이어갈 수 있다. 

### 적응성

ReAct는 처음부터 모든 계획을 고정하지 않는다.

각 Observation이 다음 Thought의 입력이 되기 때문에, 예상 밖 상황에 유연하게 대응할 수 있다.

예를 들어 다음과 같은 상황이 생길 수 있다.

- 도구 호출이 실패한다.
- 검색 결과가 비어 있다.
- 사용자의 조건과 맞지 않는 결과가 나온다.
- 중간에 새로운 제약 조건이 발견된다.

이때 Agent는 관찰 결과를 바탕으로 다음 판단을 수정한다.

상황이 바뀌면 판단도 함께 바뀌기 때문에, 더 맥락에 맞는 응답을 만들 수 있다.

### 트레이드오프

Observation 반영은 응답 품질을 높이지만, 반복이 많아질수록 부작용도 생긴다.

| 요인 | 문제 |
|---|---|
| 반복 횟수 증가 | LLM 호출 수 증가로 비용과 지연 상승 |
| Observation 누적 | 프롬프트 길이 증가로 초반 지시사항이 희석될 수 있음 |
| 종료 조건 모호 | 불필요한 반복이 계속되며 응답이 오히려 불안정해질 수 있음 |

따라서 관찰 반영 자체는 품질을 높이는 핵심 메커니즘이지만, **무한정 관찰만 반복하는 것**이 정답은 아니다.

적절한 시점에 반복을 멈추는 설계가 함께 있어야 진짜 품질 향상으로 이어진다.

---

## 7. ReAct Pattern 설계 시 주의점

ReAct Pattern이 항상 완벽한 것은 아니다.

### Observation의 신뢰성을 평가해야 한다

검색 결과나 외부 도구의 결과가 항상 정확한 것은 아니다.

잘못된 Observation을 그대로 믿으면 다음 Reasoning도 잘못될 수 있다.

따라서 Agent는 관찰 결과를 무조건 수용하는 것이 아니라, 신뢰할 수 있는 정보인지 평가해야 한다.

### 종료 조건이 필요하다

Agent가 문제를 명확히 이해하지 못하면 같은 검색이나 의미 없는 도구 호출을 반복할 수 있다.

좋은 ReAct Agent는 언제 더 행동해야 하는지뿐 아니라, 언제 멈추고 최종 답변을 해야 하는지도 판단할 수 있어야 한다.

### 모든 문제에 ReAct가 필요한 것은 아니다

간단한 개념 질문에는 여러 번의 도구 호출이 필요하지 않을 수 있다.

반대로 최신 정보, 복잡한 조건, 여러 단계의 의사결정이 필요한 문제에서는 ReAct가 더 효과적이다.

---

## 8. 정리

ReAct Pattern은 Agent가 문제를 해결할 때 **Reasoning과 Acting을 반복하는 구조**이다.

이 구조에서 중요한 점은 행동 이후의 **Observation을 다음 판단에 반영한다는 것**이다.

이를 통해 Agent는 다음과 같은 장점을 얻는다.

- 잘못된 가정을 수정한다.
- 최신 정보와 실제 데이터를 반영한다.
- 복잡한 문제를 단계적으로 해결한다.
- 더 정확하고 맥락에 맞는 응답을 생성한다.

결론적으로 ReAct Pattern은 Agent를 단순한 답변 생성기에서, **상황을 관찰하고 판단을 갱신하는 문제 해결자**로 만들어주는 핵심 패턴이라고 할 수 있다.
