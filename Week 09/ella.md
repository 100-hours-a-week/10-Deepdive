# FP32, FP16, INT8, INT4가 LLM 추론에서 연산 정밀도, 메모리 사용량, 추론 속도, 응답 품질에 어떤 차이를 만드는지 설명하시오

## 0. 정밀도와 양자화

### 정밀도 Precision

정밀도는 숫자를 얼마나 세밀하게 표현할 수 있는지를 의미한다.

예를 들어 FP32는 32비트를 사용해 하나의 숫자를 표현하고, FP16은 16비트를 사용한다.

비트 수가 많을수록 더 넓은 범위와 더 세밀한 값을 표현할 수 있다.

하지만 그만큼 메모리 사용량과 연산 비용이 증가한다.

### 양자화 Quantization

양자화는 모델의 가중치를 더 낮은 비트 수로 변환하는 기법이다.

예를 들어 FP16 가중치를 INT8이나 INT4로 바꾸면, 모델 크기를 크게 줄일 수 있다.

대신 숫자 표현이 거칠어지기 때문에 품질 저하 가능성이 생긴다.

---

## 1. 왜 정밀도가 문제인가

LLM은 수십억 개의 **파라미터, 즉 숫자**로 이루어진 모델이다.

**추론**: 이 숫자들을 메모리에서 읽어와 곱하고 더하면서 다음 토큰을 예측하는 과정이다.

따라서 숫자 하나를 **몇 비트로 저장하고 계산하느냐**가 다음 네 가지를 동시에 바꾼다.

1. 연산 정밀도: 얼마나 세밀하게 계산하는가
2. 메모리 사용량: 모델이 GPU 메모리에 올라가는가
3. 추론 속도: 토큰이 얼마나 빨리 생성되는가
4. 응답 품질: 답변이 얼마나 안정적으로 유지되는가

---

## 2. 데이터 타입

| 포맷 | 비트 수 | 파라미터당 크기 | 표현 방식 | 특징 |
|---|---:|---:|---|---|
| **FP32** | 32bit | 4 byte | 부호 1 + 지수 8 + 가수 23 | 학습의 기준점, 추론에는 무거움 |
| **FP16** | 16bit | 2 byte | 부동소수점 | 현대 GPU 추론의 사실상 표준 |
| **INT8** | 8bit | 1 byte | 정수 + 스케일 팩터 | 양자화 시작점, 품질 손실이 보통 작음 |
| **INT4** | 4bit | 0.5 byte | 정수 + 그룹별 스케일 | 극한 압축, 로컬 LLM에서 많이 사용 |

### 부동소수점 vs 정수

- **FP, 부동소수점**: 소수점 위치가 움직이므로 아주 크거나 작은 수도 표현 가능
- **INT, 정수**: 소수점이 없으므로 실수 가중치를 정수로 **매핑, 즉 양자화**해야 함

```text
양자화의 기본 아이디어:

실수 가중치 w  ->  round(w / scale)  ->  정수 q
복원할 때:      q * scale  ~=  w

오차 = 양자화 손실
```

## 3. 메모리: 7B 모델로 계산해 보기

파라미터 70억 개, 즉 7B 모델의 **가중치만** 단순 계산하면 다음과 같다.

| 정밀도 | 계산 | 필요 메모리 | Colab T4 16GB에서? |
|---|---|---:|---|
| FP32 | 7B x 4 byte | **약 28GB** | 불가능 |
| FP16 | 7B x 2 byte | **약 14GB** | 아슬아슬, 실전에서는 위험 |
| INT8 | 7B x 1 byte | **약 7GB** | 비교적 여유 |
| INT4 | 7B x 0.5 byte | **약 3.5GB** | 넉넉, 로컬 실행도 가능 |

실제 추론에서는 가중치 외에도 다음 메모리가 추가로 필요하다.

- **KV cache**: 이전 토큰의 key/value를 저장하는 캐시
- **Activation**: 중간 계산값
- 런타임 오버헤드

그래서 "14GB 모델을 16GB GPU에 올린다"는 말은 이론상 가능해 보여도, 실제로는 OOM이 날 수 있다.

> OOM: 시스템이나 프로그램이 할당받거나 사용 가능한 메모리를 모두 소진하여 더 이상 작업을 처리할 수 없는 상태나 오류

---

## 4. 속도: 왜 비트를 줄이면 빨라지는가

핵심은 LLM 추론이 많은 경우 **연산량보다 메모리 대역폭에 묶인다**는 점이다.

이를 **memory-bound**라고 한다.

토큰을 생성할 때 모델은 대부분의 레이어 가중치를 반복적으로 메모리에서 읽어야 한다.

이때 GPU 연산 유닛은 충분히 빠른데, 데이터가 메모리에서 도착하기를 기다리는 시간이 병목이 될 수 있다.

따라서 가중치 크기를 줄이면 읽어올 데이터가 줄어들고, 토큰 생성 속도가 빨라질 수 있다.

### 추가 가속 요인

- **FP16**: Tensor Core가 FP16 행렬곱을 하드웨어 수준에서 가속
- **INT8**: 정수 연산 유닛과 최적화된 커널을 활용 가능
- **INT4**: 저장은 4bit로 하고, 연산 직전에 FP16 등으로 복원하는 방식이 자주 사용됨

### 주의할 점

저비트라고 해서 항상 더 빠른 것은 아니다.

속도 이점은 다음 조건에 의존한다.

- 하드웨어가 해당 비트 연산을 잘 지원하는가
- 추론 엔진과 커널이 최적화되어 있는가
- 역양자화 오버헤드가 메모리 절감 이득보다 작게 유지되는가

최적화가 부족한 환경에서는 INT4가 FP16보다 느릴 수도 있다.

## 5. 응답 품질: 얼마나 잃는가

| 정밀도 변화 | 품질 영향 | 비고 |
|---|---|---|
| FP32 -> FP16 | 거의 없음 | 추론에서는 사실상 무손실에 가깝게 사용 |
| FP16 -> INT8 | 보통 작음 | 이상치(outlier) 처리와 보정 기법이 중요 |
| INT8 -> INT4 | 체감 가능해질 수 있음 | GPTQ, AWQ 등으로 손실 최소화 |

품질 손실은 항상 문장이 어색해지는 방식으로만 나타나지 않는다.

다음 작업에서 먼저 드러나는 경우가 많다.

- 수학 문제
- 코드 생성
- 긴 문맥 추론
- 여러 조건을 끝까지 따라야 하는 지시 수행

또한 모델이 작을수록 양자화에 더 취약할 수 있다.

예를 들어 7B 모델의 INT4 손실이 70B 모델의 INT4 손실보다 더 크게 체감될 수 있다.

### 핵심 트레이드오프

같은 VRAM 안에서는 **큰 모델의 INT4**가 **작은 모델의 FP16**보다 더 좋은 결과를 내는 경우도 많다.

즉 정밀도만 볼 것이 아니라, 모델 크기와 하드웨어 제약을 함께 봐야 한다.

---

## 6. 실전에서는 어떻게 쓰이나

| 상황 | 주로 쓰는 정밀도 |
|---|---|
| 학습 | FP32 또는 혼합 정밀도 |
| 서버 추론, API 서비스 | FP16 / BF16 기본, 트래픽이 많으면 INT8 고려 |
| 로컬 LLM | INT4 계열 양자화 모델을 많이 사용 |
| 엣지/개인 장비 | INT4, 경우에 따라 INT8 |

### 상황별 선택 기준

| 상황 | 추천 |
|---|---|
| 최고 품질과 안정성이 우선 | FP16 / BF16 |
| GPU 메모리가 부족 | INT8 -> INT4 |
| 많은 요청을 동시에 처리 | FP16, INT8 |
| 개인 장비에서 큰 모델 실행 | INT4 |
| 수학, 코드, 정밀 추론이 핵심 | FP16 이상 권장 |

---

## 7. 요약

| 관점 | FP32 | FP16 | INT8 | INT4 |
|---|---:|---:|---:|---:|
| 메모리, 7B 기준 | 약 28GB | 약 14GB | 약 7GB | 약 3.5GB |
| 속도 | 기준 | 빠름 | 더 빠를 수 있음 | 가장 빠를 수 있음, 환경 의존 |
| 품질 | 기준 | 거의 동일 | 보통 거의 유지 | 소폭 손실 가능 |
| 용도 | 학습, 기준값 | 서버 추론 표준 | 대규모 서빙 최적화 | 로컬/엣지 LLM |

**결론**

정밀도 선택은 **품질과 자원의 트레이드오프**이다.

LLM 추론은 memory-bound인 경우가 많기 때문에 비트를 줄이면 메모리와 속도에서 큰 이득을 얻을 수 있다.

다만 비트를 낮출수록 숫자 표현이 거칠어지고, 수학, 코드, 긴 문맥 추론 같은 민감한 작업에서는 응답 품질 리스크가 커질 수 있다.
